🚀 Pipeline CI/CD Microservices — Déploiement automatisé

📋 Contexte & Problématique

Au sein de l'équipe DevOps de Thales, les déploiements d'applications microservices étaient réalisés manuellement, engendrant des erreurs humaines fréquentes et des délais importants (plusieurs heures par livraison). J'ai été chargé de concevoir et d'implémenter une chaîne CI/CD complète pour automatiser l'intégralité du processus.

🎯 Objectifs

Réduire le temps de déploiement, éliminer les interventions manuelles, garantir la qualité du code à chaque commit et sécuriser les images Docker avant mise en production.

🛠️ Stack technique

GitLab CI/CD, Docker, Kubernetes, Trivy (scan de vulnérabilités), Snyk, pytest (tests unitaires), Registry GitLab.

👤 Mon rôle

Conception de l'architecture CI/CD, rédaction du fichier .gitlab-ci.yml, mise en place des stages, configuration des runners GitLab et intégration des outils de sécurité.

📄 Description des stages
  • Build : Construction de l'image Docker et push vers le GitLab Container Registry, taguée avec le SHA du commit pour une traçabilité complète.
  • Test : Exécution des tests unitaires avec pytest et mesure de la couverture de code. Les tests d'intégration vérifient les appels inter-services.
  • Security : Scan de l'image Docker avec Trivy pour détecter les vulnérabilités CVE. Le pipeline échoue automatiquement si une vulnérabilité critique est détectée.
  • Staging : Déploiement automatique sur l'environnement de staging via kubectl set image. Vérification du rollout avant de continuer.
  • Production : Déploiement manuel déclenché par validation humaine (when: manual), uniquement sur la branche main. Garantit un contrôle avant chaque mise en production.

// Extrait .gitlab-ci.yml

stages: [build, test, security, deploy-staging, deploy-prod]

build-docker:
  stage: build
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA

unit-tests:
  stage: test
  image: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
  script: pytest tests/ -v --cov=app
  coverage: '/TOTAL.+?(\d+\%)/'

trivy-scan:
  stage: security
  script:
    - trivy image --exit-code 1 --severity HIGH,CRITICAL $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA

deploy-prod:
  stage: deploy-prod
  script:
    - kubectl set image deployment/app app=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
    - kubectl rollout status deployment/app
  when: manual
  only: [main]

☸️ Orchestration Kubernetes — Déploiement multi-environnements

📋 Contexte & Problématique

Dans le cadre de la conteneurisation des applications Thales, il était nécessaire d'orchestrer les déploiements sur plusieurs environnements (staging et production) avec des garanties de disponibilité et de montée en charge. J'ai mis en place une architecture Kubernetes complète couvrant l'ensemble des ressources nécessaires.

🎯 Objectifs

Garantir la haute disponibilité des applications, automatiser le scaling horizontal, assurer les mises à jour sans interruption de service et monitorer l'état des pods en temps réel.

🛠️ Ressources déployées

Deployment, Service (ClusterIP / NodePort), Ingress (nginx), ConfigMap, Secret, HorizontalPodAutoscaler (HPA), ResourceQuota par namespace.

👤 Mon rôle

Rédaction des manifestes YAML, configuration des namespaces, mise en place du rolling update, configuration des health checks (liveness & readiness probes) et tests de montée en charge.

📄 Architecture Kubernetes mise en place
  • Deployment : 3 réplicas avec stratégie RollingUpdate (maxSurge: 1, maxUnavailable: 0) pour garantir la continuité de service lors des mises à jour.
  • Service : Exposition interne via ClusterIP, accès externe via Ingress nginx avec terminaison TLS.
  • HPA : Autoscaling horizontal configuré entre 2 et 10 réplicas selon la charge CPU (seuil à 70%).
  • ConfigMap & Secret : Externalisation de la configuration applicative et gestion sécurisée des credentials.
  • Probes : Liveness probe sur /health et readiness probe sur /ready pour garantir que seuls les pods sains reçoivent du trafic.

Réseau Windows Server Active Directory

🌐 Infrastructure Réseau Sécurisée avec Active Directory

📋 Contexte & Problématique

Dans le cadre du BTS SIO, ce projet consistait à concevoir et déployer une infrastructure réseau complète pour une PME fictive de 50 utilisateurs. L'objectif était de mettre en place un environnement Windows Server avec Active Directory, segmenté en VLANs, avec des politiques de sécurité GPO adaptées à chaque profil utilisateur.

🎯 Objectifs

Centraliser l'authentification, segmenter le réseau par VLAN, appliquer des stratégies de sécurité GPO et assurer les services DHCP/DNS pour l'ensemble du parc.

🛠️ Environnement

VirtualBox, Windows Server 2022 (Contrôleur de domaine), Windows 10/11 (postes clients), routeur Cisco inter-VLAN, commutateur manageable.

👤 Mon rôle

Conception du plan d'adressage IP, installation et configuration du serveur AD DS, création de l'arborescence OU, déploiement des GPO et tests de validation.

📄 Détail des composants déployés
  • Active Directory DS : Création du domaine pme.local, arborescence d'unités organisationnelles (OU) par service (Direction, Comptabilité, Informatique, RH), groupes de sécurité et délégation d'administration.
  • DHCP : Serveur DHCP configuré avec des plages d'adresses par VLAN, réservations statiques pour les serveurs et exclusions pour les équipements réseau.
  • DNS : Zone de recherche directe et inverse pour le domaine interne, redirecteurs configurés vers les DNS publics (8.8.8.8) pour la résolution externe.
  • GPO : 8 stratégies de groupe déployées couvrant la sécurité des mots de passe, les restrictions logicielles et la redirection de dossiers.
  • Segmentation VLAN : 3 VLANs configurés sur le commutateur et le routeur Cisco pour isoler les flux Administration, Utilisateurs et DMZ.

🖥️ Gestion de Parc Informatique avec GLPI

📋 Contexte & Problématique

Ce projet visait à déployer une solution ITSM open source pour centraliser la gestion du parc informatique d'une entreprise fictive. Sans outil centralisé, le suivi des incidents, l'inventaire matériel et la gestion des contrats étaient réalisés sur des fichiers Excel épars, rendant toute intervention difficile à tracer.

🎯 Objectifs

Centraliser l'inventaire matériel et logiciel, mettre en place un système de tickets pour le support utilisateur, et assurer le suivi des contrats de maintenance.

🛠️ Stack technique

GLPI 10, FusionInventory (agent d'inventaire automatique), serveur Apache/MySQL sous Debian, intégration LDAP avec Active Directory.

👤 Mon rôle

Installation du serveur GLPI, configuration de FusionInventory, création des profils utilisateurs, paramétrage des SLA et formation des utilisateurs à l'outil.
